# System audit — BOR-81 / BOR-82 / BOR-90 (2026-08-15)

Scope: the whole Tasty ERP repository — three Spring Boot services, the shared
`common` module, the React frontend, Docker/Caddy deployment, CI. This document
is the record the three tickets ask for: the diagnostic stack used, the audit
findings across every domain, a five-step deep dive for every fix that shipped,
the memory evidence, and what remains open with a recommendation for each.

Companion artefacts: `firestore.indexes.json` + `firebase.json` (new),
`tasty-erp-frontend` test harness (new), the "Engineering rules" section added
to `CLAUDE.md`.

## 5. Five-step deep dives (one per shipped fix)

Format: Symptom → Trigger → Code flaw → Architectural gap → Root correction (+ regression test).

**B-3 — interrupt-flag poisoning / outage-as-empty.**
1. `/audit` returns HTTP 200 with every classified lari shown as unresolved, supplier debt 0, checks 0, real stock 0.
2. One transient Firestore `DEADLINE_EXCEEDED`/`FAILED_PRECONDITION` during `loadMappingIndex()`.
3. `AuditLayerRepository.findAllMappings` (and 12 siblings) caught `InterruptedException | ExecutionException`, logged, called `Thread.currentThread().interrupt()`, returned `[]`. The flag then made `findSupplierDebts`, `findCheckEvidence`, `findRealInventory` fail instantly with `InterruptedException` — each also returning `[]`.
4. Two unrelated failure modes conflated in one catch; "no data" used as the error channel. `PaymentRepository` had already been burned by exactly this and fixed it locally (`readFailure`), but the idiom was never swept — 64 sites across three services.
5. `common.util.FutureResults.await(future, context)`: bounded wait, interrupt flag only on `InterruptedException`, `DataStoreException` (503) on everything else. Audit repository, bank-row loader and `CustomerRepository.findAll` now throw; the other 44 sites were mechanically split so `interrupt()` runs only in the `InterruptedException` branch (behaviour otherwise preserved). Tests: `FutureResultsTest` (flag not set on ExecutionException; preserved on real interruption; timeout cancels).

**B-4 — unit-classification drift.**
1. Different kilograms for the same period on `/audit` vs `/audit-control`; the gap column understated.
2. Any RS.ge line whose unit is spelled out (`კილოგრამი`, `kilogram`).
3. `AuditFlowService.isKilogram` lacked the positive-kg short-circuit; `"კილოგრამი"` contains `"გრამ"` (gram) → non-kg.
4. Rule copied into three classes; only `ProductCategoryResolver` had been extracted.
5. `common.util.UnitClassifier`; three delegations. Test: `UnitClassifierTest` (28 cases incl. the spelled-out forms).

**B-5 — manual-cash import doubling.**
1. Customers appear paid up who are not; `currentDebt` drops by the duplicated amount.
2. Browser timeout mid-upload → operator re-uploads the same file.
3. `ManualCashExcelImportService` built no `uniqueCode`, loaded no existing set, and called `save()` (random UUID) per row.
4. Idempotency was a property of *one* importer (bank path) rather than of the write path.
5. Deterministic ids `mcx|date|amountCents|customerId|ordinal`, pre-load of existing after-cutoff receipts to report duplicates, in-file ordinal for genuine same-day repeats, batched `saveAll`. Test: `ManualCashExcelImportServiceTest` (first upload deterministic; re-upload adds 0 and reports 3 duplicates; legacy random-id rows count toward identity).

**B-9 / F-11 / M-3 — cache stampede and pinned expired values.**
1. Three operators opening the audit page in the same second on a cold cache tripled a 147 s RS.ge fetch; expired multi-year feeds stayed on the heap until 16 other ranges arrived.
2. Concurrent misses; distinct date ranges over an afternoon.
3. `SimpleTtlCache.getOrCompute` loaded outside any per-key guard; expiry only pruned on a `put` at the bound.
4. "Thread-safe map" was mistaken for "thread-safe load"; eviction designed for key count, not value size.
5. Single-flight via per-key `CompletableFuture`; expired entry removed on read; sweep on every miss + `sweepExpired()`; `maxEntries` 16 → 4 for the two movement caches; `named(...)` registry for diagnostics. Tests: `SimpleTtlCacheTest` (+4: 12-thread stampede loads once; expired freed on read; swept on miss; failing loader not cached).

**F-1 — categories per row.** 1. One drill-down click takes minutes and burns two days of Firestore quota. 2. `cash.supplierSettlement`. 3. `hasSupplierSettlement(row)` called `mappingService.categoriesByCode()` (a collection read) inside the per-row predicate. 4. `Predicate<Row>` had nowhere to hang loop-invariant context, so a repository call leaked into the loop; the same mistake had been fixed once for history but not generalised. 5. Loaded once in `expand`, captured by the lambda; predicate is `static` and pure. Test: `AuditDrilldownServiceTest` (500 rows → `categoriesByCode` called once).

**F-7 — revokeRule.** 1. Revoking a rule that mapped thousands of rows takes minutes and can leave it half-revoked. 2. `DELETE /mappings/rules/{id}`. 3. Full-collection scan + `saveMapping` per row. 4. The batching primitive (`saveMappingsBatch`) existed and was used by `apply()` but not by revoke; no keyed query. 5. `findMappingsByRuleId` (equality on `appliedByRuleId`, auto-indexed) + one batch + one history entry per row. Test: `AuditMappingRuleServiceRevokeTest`.

**F-9 — change log.** 1. `GET /change-log` grows linearly with history. 2. Any call without `entityId`. 3. Whole collection read, sorted, then `limit`. 4. "Small relative to source collections" stopped being true after bulk suggestion runs (one entry per row). 5. `orderBy(changedAt desc).limit(n)` in the query (ISO string sorts chronologically; single-field index is automatic); `subList` copied. Composite `(entityId, changedAt)` declared for the per-entity path.

**B-10 — null amount.** 1. Whole debt page 500s. 2. One waybill with `"amount": null`. 3. `getOrDefault` does not default a present-null; `new BigDecimal("null")`. 4. JSON-map coercion done ad hoc. 5. `DebtService.jsonDecimal` (null/absent/garbage → 0 with a WARN). Test in `DebtServiceParityTest`.

**B-11 / M-6 — TBC client per page.** 1. Thread and native-memory drip on every hourly sync; cold TLS handshake per page. 2. `getAccountMovements` paging loop. 3. `postSoap` built `HttpClient` + `SSLContext` + parsed PKCS12 per call; Java 17 `HttpClient` has no `close()`. 4. `RsGeSoapClient` already held a singleton client; the TBC port did not follow it. 5. Cached client keyed on certificate config (not the WS-Security password); factory seam for tests. Test: `TbcDbiClientHttpClientReuseTest`.

**B-12 — empty goods dead code.** 1. Every goods-less waybill is a permanent RS.ge round trip on every request. 2. Any waybill without a `WAYBILL` body. 3. `getWaybillGoodsMap` dropped empty results before the caller's "store even when empty" branch. 4. Two meanings ("fetched empty" / "failed") collapsed into one absence. 5. `GoodsFetch` record distinguishes them; empty persisted, failed omitted and retried; windowed submission (M-4); ERROR summary on partial results.

**B-14 — European amounts.** 1. `1.234,56` → 1.23. 2. String-typed amount cells. 3. Separator chosen by presence, not position. 4. No test for the European form. 5. Last separator wins. Test added to `AmountUtilsTest`.

**M-1 / M-2 — JVM sizing.** 1. Silent `exit 137` restarts under load. 2. Heap filling to its 75 % cap. 3. Measured: ~200 MB non-heap committed at idle (config-service RSS 244 MB with 64 MB heap; payment-service 256 MB with 74 MB) — so 75 % + non-heap > limit. 4. The deployment guide reasoned about heap only. 5. Heap 60 %/40 %, explicit Metaspace/direct caps, `ExitOnOutOfMemoryError`, config-service 256 → 512 MB, rationale in the Dockerfiles. Diagnostics: `MemoryDiagnostics` (tested).

**M-10 — common pool.** 1. "Parallel" SALE/PURCHASE fetch is serial in prod. 2. 0.5-CPU container → common-pool parallelism 0. 3. `supplyAsync` without executor. 4. Executor choice invisible at the call site. 5. Dedicated 2-thread daemon executor.

**O-1 — correlation.** 1. Cannot join a payment-service line to the config-service line that served it. 2. Every internal call. 3. No `ClientHttpRequestInterceptor`; config-service pattern lacked `%X{requestId}`. 4. Filter and clients built separately. 5. `RequestIdPropagatingInterceptor` on both templates; pattern aligned. Test: `RequestIdPropagatingInterceptorTest`.

**FE-1/FE-2/FE-3/FE-5/FE-6/FE-8/FE-10/FE-13/FE-14/FE-21/O-6/O-7** — see the table; each root fix names the gap in a code comment at the site, and the hook/badge/toast/formatter behaviour is pinned by `use-audit-flows.test.tsx`, `rule-badge.test.tsx`, `query-client.test.tsx`, `utils.test.ts`.

## 6. Memory audit (BOR-90) — evidence and conclusions

**Method.** Inventory of every memory consumer (caches, pools, clients, in-flight payloads, MDC, listeners, schedulers, frontend effects/caches), then measurement of the two services that carry the risk, with the production heap caps, idle after warm-up, JDK 25 locally (production is JRE 17 Alpine; Metaspace/CodeCache/thread figures are comparable, G1 tables somewhat lower on 17).

**Measurements (idle, after Firestore warm-up and a few actuator calls).**

| Service | Cap | Heap committed | Non-heap committed (NMT) | RSS | Threads |
|---|---|---|---|---|---|
| config-service | 256 MB limit, `-Xmx192m` (=75 %) | 64 MB | ≈ 200 MB (Metaspace 58, GC 62, Code 25, CDS 14, Symbol 13, threads 3.5, other ~25) | **244 MB** | 38 |
| payment-service | 768 MB limit, `-Xmx576m` (=75 %) | 74 MB | ≈ 200 MB | **256 MB** | 67 |

JIT/compiler arenas peaked at ~170 MB *transiently during start-up* (NMT peak columns) — start-up alone can brush a 256 MB cgroup.

**Conclusions.**
1. **No unbounded (classic) leak was found** in the Java services or the frontend: every service-held collection is bounded or per-request; every frontend effect cleans up; MDC is cleared; there are no Firestore listeners; the one `@Scheduled` job holds no state.
2. The verified risks were: (a) JVM sizing that could not fit — a full heap put RSS above the cgroup limit, killed silently; (b) caches pinning expired multi-year feeds (up to 16 per service); (c) unbounded executor queues + double materialisation on the RS.ge goods path; (d) the per-call TBC `HttpClient` (threads/native memory outside the heap); (e) POI loading a 10 MB `.xlsx` as a full DOM twice (bounded, but two concurrent uploads could exceed the heap).
3. Corrections shipped for (a)–(d). (e) is bounded by the multipart cap; recommendation in §8.
4. Observability added: `MemoryDiagnostics` line every 5 min with cache sizes; `ExitOnOutOfMemoryError` turns a hidden kill into a logged OOM + restart; `MaxMetaspaceSize`/`MaxDirectMemorySize` make a leak in those areas a Java `OutOfMemoryError` with a stack rather than a cgroup kill.

**Verification limits.** A sustained production-like workload was *not* run against production Firestore/RS.ge from this environment (it would consume real quota and hit RS.ge). Regression tests pin the boundedness properties (single-flight, expiry, HttpClient reuse, windowed fetch). After deploy, the `MEM heap …` series in `docker compose logs` is the before/after evidence for the VM: it should plateau after warm-up and return toward baseline after wide-range audit loads.

## 11. `/audit` overview strip and two-level mappings (2026-08-15, BOR-92)

**Ask:** the top of `/audit` must read *purchases | total | chosen*, *bank payments to suppliers | total | to chosen*, *cash outflow | total | unmapped*, *sales | total | real*, each clickable; cash outflow grouped by user-created groups with a document-status level ("purchase act needed", "check needed", "got check", "unmapped", extensible) and a counterparty per slice; net stock on paper per product group attributed to suppliers; unreal sales chained onward as paper cash-out under the exact supplier. Decisions taken with the user: *chosen* = a supplier filter; two levels = group (existing categories) + document status + counterparty; the unreal→supplier chain shows as **paper** cash-out and is never added to real money; stock by supplier is **LIFO**.

**Backend** (`payment-service`, one endpoint, one pure builder):
- `GET /api/audit-control/layer/overview?startDate&endDate&supplierTin` → `AuditOverviewDto`; `AuditOverviewService.build(...)` is static and pure (tests feed it rows). Definitions live in the DTO javadoc and are repeated on the tiles.
- Level 2: `AuditMappingSplitDto.subgroupCode`; `AuditSubgroups` built-ins + `audit_subgroups` custom collection; `GET/POST/DELETE /layer/subgroups`. `validateSplits` rejects unknown codes; deleting a status still on a live split is refused with the count.
- Cash-outflow tree: group (category) → status (`NONE` when absent) → counterparty (slice TIN, else the row's resolved TIN); the uncovered remainder is its own `UNMAPPED` group so "unmapped" on the tile and in the tree is the same number.
- Paper tree: SALE document rows to unreal customers whose splits carry a supplier-ish category → group → status → supplier; `paperTotal` is shown beside `total`, never inside it.
- Inventory: `net = purchased − writeOff(rate, default 28 %) − sold` per category, then `lifo(lots)` walks purchases backwards until net is covered. Opening stock is unknown, so the DTO calls this a movement and `notes` says so.
- Tests: `AuditOverviewServiceTest` (6), `AuditMappingServiceTest` +4 (subgroup validation / in-use guard).

**Frontend:** `components/audit/overview/overview-strip.tsx` (picker + 4 tiles + panels), `counterparty-picker.tsx` (datalist of suppliers-in-period + customer register; exact match attaches the TIN, free text never guesses one), `subgroup-manager.tsx` (Rules section), mapping editor gains a *Document status* select and the counterparty picker per split. `useAuditOverview` is in `MAPPING_SCOPES`, so a save in the workbench moves the strip. Tests +7 (36 total).

**Rules honoured (CLAUDE.md):** statuses and groups are user-extensible; "chosen" with no supplier renders `—` and says why, not `0`; each tile's drill-down is its own record set; the outflow "map" button targets `cash.unresolvedWithdrawals` only.

### 11.1 v2 — statement instead of tiles (2026-08-16)

Feedback on v1: the four tiles overlapped at some widths and read as boxes, not as a
statement. Rebuilt as **one ledger** with rows in income-statement order —
Purchases → Bank payments to suppliers → Cash outflow → Inventory (net, on paper) →
Sales → Bank inflow (payments from customers) → Cash inflow (cash from customers) —
and two figure columns, **Total | Chosen**.

- **Chosen** is now a *saved selection*, not a picker: inside each row's window every
  counterparty has a checkbox. Supplier-side rows share one supplier set, customer-side
  rows share one customer set; both are stored per operator name
  (`audit_statement_selection/{operator}`) so they survive reloads and devices. Writes are
  debounced; the local ticks win until the server agrees. Nothing ticked → `—` + "nothing
  ticked", never 0.
- **Every row opens a window** (`StatementDialog`, wide): parties with ₾ / kg / lines and
  a chevron that unfolds the transactions in place (`GET /layer/statement/transactions`).
  Purchases and Sales carry a second sheet, **Products** (by product group); a group
  unfolds to its lines, where a line's group can be changed. That is the shared product
  rule (`PUT /layer/product-categories`), so the confirmation says: exact product name,
  purchases *and* sales, both pages, and how many loaded lines carry the name.
- **Inflows are not recomputed**: bank inflow reads `PaymentRepository.findBankPayments`
  and cash inflow `findManualPayments` — the same collections the /payments page lists.
- **Inventory** is a row: Σ net kg and its value at the period's average purchase price
  per kg per group (unpriced groups are named, not zeroed); the window shows the levels
  with the LIFO supplier attribution.
- **Bug found on the way:** `AuditConfigClient.categoryOverrides()` read `productName`

### 11.5 v6 — a non-RS.ge counterparty appeared in Purchases: five whys, fix, and the checks that now guard it (2026-08-18)

**Symptom.** ნუკრი ბოშიშვილი (TIN 12001020993) was listed as a supplier in the Purchases window
with 0 ₾ purchases, 525,443 ₾ "bank paid" and −525,443 ₾ "unpaid after bank". RS.ge has no purchase
document from that counterparty.

1. *Why was it listed?* v3 inserted every counterparty of a supplier-settlement bank slice into
   the Purchases party map (`sellers.computeIfAbsent(cp, …)`) so that "paid, undocumented" would
   show as a negative remainder — a design shortcut of mine, not a data problem.
2. *Why did the slices exist?* A rule the operator created ("Every payment to ნუკრი ბოშიშვილი",
   72 auto + 1 manual rows) maps those debits to *Supplier bank payment*. A rule can say that;
   the statement should not have let it define who is a supplier.
3. *Why did the row's title and its list disagree?* The row's definition ("₾ of every RS.ge
   purchase document line") described the total, but the party list drew on a second source
   (bank slices). Two sources under one heading; nothing asserted the list ⊆ RS.ge sellers.
4. *Why was it not caught before deploy?* No invariant test: nothing checked that every Purchases
   party has ≥ 1 document line, that Σ parties = row total, or that lines = what RS.ge says the
   documents total. The unit tests asserted hand-computed figures, not the shape of the payload.
5. *Why could the frontend show something the API did not send?* There was no reconciliation
   between what the API aggregates and what the page renders — the page trusted the payload, and
   the payload trusted its own arithmetic.

**Fix.**
- Purchases lists RS.ge sellers only (`AuditSupplierRegistry.from(movements)` — the period's
  purchase documents; the same registry `AuditFlowService` uses). "Bank payments to suppliers"
  counts a supplier-settlement slice only when its counterparty is such a seller; the rest is
  reported beside the row (*mapped as supplier payment, not on RS.ge*), flagged on the party in
  Cash outflow, and named in a note — never counted as a supplier payment. Withdrawals-to-suppliers
  applies the same test.
- **Self-checks** on every statement payload (`AuditStatementDto.checks`, `AuditStatementService.checks`):
  Σ parties = row (6 rows), Σ product groups = row (2), Purchases has RS.ge sellers only, bank
  inflow split adds up, withdrawals split adds up, and **RS.ge document totals vs goods lines**
  for purchases and sales — from a new `GET /api/waybills/document-totals` (waybill-service,
  same waybills and stored goods as the movements; counts waybills without goods and waybills whose
  lines ≠ FULL_AMOUNT). A failed check is a red line under the table with expected/shown/detail
  and a note; a missing input is SKIPPED, never PASSED. Failed checks are logged WARN.
- **On-screen check** in every window: the counterparties rendered are summed and compared with
  the row rendered; a mismatch shows an alert on that screen.
- Tests: `AuditStatementServiceTest` (RS.ge-only rule, checks pass / tamper → FAILED / missing →
  SKIPPED), `InventoryMovementServiceTotalsTest`, FE 41.
